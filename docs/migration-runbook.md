# ترحيل SpectraVision من v1 إلى v2

## خط الأساس

- Git commit `a79f8f9c627a057ed575d3f0024920d1a783a564` يحتوي على v1.
- SHA-256 لمثبّت 1.0.0 هو `2ff172e6d401d9d602c0dbe9cd4120d79864524408273d5bdfec14af04259b5f`.
- SHA-256 لملف `ESPWorkbench.exe` من حزمة 1.0.0 هو `de353b41c745c6f55cba0c1cab7e26bfb1636dff46b2517a0d35d5c6c7907641`.
- مفتاح التحديث العام لكل من v1 وv2 في `installer/update-keys.json`. تم التحقق من توقيع بيان 1.0.0 بالمفتاح القديم.
- قاعدة `spectravision-licenses` للإنتاج تستخدم المعرّف الموجود في `licensing/wrangler.jsonc`. جرد القراءة في 11 نوفمبر 2026 وجد ترخيصًا واحدًا وجهازًا واحدًا. أعد الجرد وقت التنفيذ.
- Staging تستخدم `spectravision-licenses-staging` بمعرّف مستقل. بيانات الاختبار مصطنعة.

## الترحيل

1. شغّل اختبارات القبول على Staging. اختبر الحساب المسموح والمرفوض ومصفوفة Windows على جهاز نظيف.
2. من حساب Cloudflare راجع حصة Free. جهز حماية Access لـAdmin Worker وقيمه لكل بيئة باتباع دليل التشغيل.
3. احتفظ بالمثبّت القديم وبيان توقيعه. صدّر قاعدة الإنتاج إلى مكان آمن إذا كانت سياسة التخزين تسمح. خزّن النسخة مشفّرة خارج Git.
4. شغّل `Deploy production` يدويًا من `main` بعد اعتماد اختبارات Staging. وافق على GitHub Environment بعد مراجعة الـcommit. يسجل التنفيذ Bookmark ويقارن الأعداد قبل وبعد الترحيل. راجع سجل أي تغييرات متزامنة في v1 إذا فشلت مطابقة الأعداد.
5. طبّق `0003_cloud_control.sql` كترحيل إضافي. أبقِ Worker v1 ومسارات `/api/activate` و`/api/verify` متاحة طوال فترة الانتقال.
6. فعّل إصدار الجسر على جهاز المطوّر ثم 3–5 أجهزة. تحقق من إعادة استخدام مقعد v1، ومن احتفاظ المثبّت بمساري `settings.json` و`activation.bin` تحت `%LOCALAPPDATA%\SpectraVision\Data`. انتقال الهوية v1 يحتاج أول تحقق ناجح عبر الشبكة.
7. راقب 24–48 ساعة أثناء التشغيل الفعلي قبل التعميم. تابع رفض الجلسات وحالات انقطاع الشبكة والحصص والتنزيلات.
8. ضع حدًا أدنى للإصدارات بعد التحقق من توفر المثبّت الموقّع. راجع أعداد عملاء v1 قبل إنهاء الخدمة القديمة.

شغّل استعلام المقارنة من مجلد `licensing` قبل الترحيل وبعده. استخدم اسم قاعدة Staging وملف ضبطها للاختبار.

```powershell
$query = Get-Content -Raw tests/reconcile.sql
npx --no-install wrangler d1 execute spectravision-licenses --remote --config wrangler.client.jsonc --json --command $query
```

## توقيع إصدار الجسر

يعمل أمر بناء الجسر من حساب Windows الذي يستطيع فتح المفتاح القديم المحمي بـDPAPI.

```powershell
./installer/build-release.ps1 -Version 2.0.0 -Bridge
```

ملف الجسر في `release/cloud-control/stable/2.0.0/`. يوقّع المفتاح القديم ملف `latest.json` ويثق التطبيق داخل الجسر بالمفتاحين. للتحديث من داخل v1 بعد الموافقة، ضع المثبّت الموقّع وبيانه في `licensing/public/updates/` ضمن إصدار Worker v1 المراجع. احتفظ بمثبّت 1.0.0. يدعم بيان الجسر حقول v1 ويتضمن أيضًا حقول v2. التثبيت اليدوي للجسر طريق بديل إذا تعذر إصدار بيان موقع بالمفتاح القديم.

الإصدارات التالية تبنى من `Release Windows` بعد إعداد مفتاح v2 في GitHub Environment. يخرج GitHub Release كمسودة. بعد مراجعة التوقيع والملفات انشر المسودة وسجّل `release-metadata.json` من صفحة **Releases**، ثم غيّر الإصدار الحالي من **Settings**. اجعل الإصدار المطلوب وقناة GitHub متطابقين. استخدم `sv-stable-vVERSION` للإنتاج و`sv-test-vVERSION` للاختبار.

## الرجوع

- أوقف التوسع وراجع رقم إصدار Worker قبل الرجوع. استعمل `wrangler rollback <version-id> --config <worker-config> --yes`. ارجع العامل المتأثر وحده وأعد Smoke Test.
- ارجع مؤشر القناة من Settings إلى إصدار موقّع سبق اختباره وخفّض الحد الأدنى إن لزم. المثبّت العادي يرفض ترقية إلى رقم أقدم. للرجوع اليدوي على جهاز، أغلق التطبيق ثم اختر الـEXE الموجود في مجلد الإصدار المثبّت القديم. إذا لزم إعادة التثبيت، خذ نسخة من مجلد Data قبل إزالة التثبيت.
- استعادة D1 مستقلة عن رجوع Worker. استخدم Bookmark كخيار أخير بعد مقارنة التغييرات التي ستفقدها. احتفظ بنسخة من الحالة الحالية قبل استعادة أي نقطة تاريخية. راجع فترة Time Travel المتاحة في حسابك. [Cloudflare D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)
